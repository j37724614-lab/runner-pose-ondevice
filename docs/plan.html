01 概述與範圍

這是 on-device 遷移的第一個正式元件，不是拋棄式試作。範圍只有六階段裡的 2D 姿態這一段，但這一段要做到能上線的品質與效能：一個乾淨 API 的 Swift Package，內部是零拷貝、並行、記憶體受控的推論管線；先量測證明收益，再併進主 App。

要回答的問題
一段影片在手機上抽 23 點骨架要跑多久、佔多少 CPU 核心 / 記憶體、走 ANE 與走 CPU 差多少、 FP16 相對桌面 FP32 掉多少精度？ 最重要：這份實作最佳化到什麼程度、能不能直接進主 App？
產出
一個新 repo：RunnerPoseKit Swift Package（正式模組）+ runner_pose Flutter plugin（bridge）+ BenchApp（量測薄殼）+ benchmark 報告 + 整合指南。
使用場景
開發期：BenchApp 選本地影片 → 選運算單元 → Run → 看逐階段耗時、資源、精度誤差、 naive→optimized 收益。 正式期：Flutter 主 App 直接呼叫 plugin，影片不離開裝置，只把 2D keypoints 交給後續階段。
模型
models/coreml/HRNetRunnerWholeBody23.mlpackage HRNet-W48 · 23 點 (17 body + 6 foot) · FP16 ML Program · 輸入 288×384 · 輸出 heatmap [1,23,96,72]

範圍界線

  • 本模組只負責：影片解碼 → 人物偵測 → crop → HRNet → heatmap 解碼 → 2D keypoints。 輸出 schema 對齊現有 pipeline 的 2D 關鍵點格式（joint 順序、原圖像素座標、per-joint score）， 讓後續（左右腿修正、MotionAGFormer 3D、步頻步幅、overlay）完全不用改。
  • 不含 3D lifting、關節角度、步態、多相機、two-pass 選 ID —— 這些暫時仍在 server，模組只上傳 keypoints、不再上傳整支影片。
  • 不做即時相機串流 —— 只處理已存在的影片檔（模組內建 prescan 篩出有效區段）。
  • 不改模型、不重訓、不做 QAT。（可額外轉一份 FP32 CoreML 當精度對照，見 §07。）
為什麼獨立一個 repo

它是一個被 Flutter 主 App 以 SPM 依賴引入的 Swift Package，工具鏈 （Xcode / SwiftPM / CoreML）與主 pipeline（CUDA / Linux 離線批次）完全不重疊。獨立 repo 讓它能 單獨版本控管、單獨跑單元測試、獨立疊代最佳化，而不污染主 pipeline 或主 App 的建置。從主 repo 帶過去的 只有「模型檔 + 一批測試影片 + 桌面 ground truth 腳本」。

02 前提與限制

這些條件直接決定模組的架構、最佳化空間與量測方式，先講清楚。

模型契約

  • 輸入不是整幀畫面，是「已依人物 bbox 做 affine warp 的 288×384 RGB crop」。 正規化（除以 255 等）已經包進 .mlpackage，Swift 端不要再做。
  • 輸出 schema 要對齊現有 pipeline：模組最終輸出的 2D keypoints（joint 順序見 conversion.json、座標為原圖像素、附 per-joint score）必須與現有 HRNet 階段的 CSV / JSON 逐欄位一致，否則下游（左右腿修正、MotionAGFormer、步態）要跟著改。P1 用單元測試鎖死。
  • bbox → crop 的轉換要對齊桌面：box_to_center_scale()（固定長寬比、外擴 1.25×）+ affine warp 到 288×384，來源在 hrnet/lib/utils/utilitys.py 與 transforms.py。
  • 輸出 23 張 96×72 heatmap。要拿到跟 Python 一致的座標，必須移植 DarkPose 解碼 （get_final_preds_dark()：對 heatmap 高斯模糊 + Taylor 二階修正），不能只做 argmax。
  • 轉換報告：FP32 TorchScript trace 對 PyTorch 的最大誤差約 4.9e-6，即轉換本身近乎無損；變數是 FP16 與 Swift 端 DarkPose 移植。

需要一個上游人物偵測器

HRNet 只吃單人 crop，所以要先框出人。決定採用內建 YOLO26n CoreML 偵測器 （ultralytics/yolo-ios-app 的 UltralyticsYOLO Swift Package，pin < 9.0）， 這最貼近正式 pipeline 用 YOLO 的做法。偵測、crop、HRNet、解碼各階段分開計時， 才能單獨看 HRNet 本身的成本。

Prescan 有效幀篩選 —— 偵測模型可選，在裝置上做

正式流程有一個前處理步驟 scripts/tracking/prescan_filter_valid_video.py：低成本 YOLO 每 stride=8 幀取樣一次，標記「有合格人物 bbox」（bbox 高 ≥ min_height、conf ≥ 0.25）的幀，把命中幀併成區段、 外擴 buffer_sec=1.0 緩衝、跨 max_gap_sec=1.0 的空檔併接， 得到有效區段清單。原腳本再據此輸出 clipped 影片；本模組不輸出檔案， 直接讓後段只處理清單內的幀。

  • 原腳本預設用桌面 TensorRT yolo26x engine。本模組的偵測器是 Config.detectorModel 可選：yolo26{n,s,m,l,x}.mlpackage （yolo-ios-app v8.3.0 release，COCO detect、INT8、640）或 Apple Vision，全部在裝置上跑 —— 影片不離開裝置。先以 yolo26n 為預設，跑完 §08 效能 / 精度矩陣再定案。
  • S0 prescan 與 §03 S2 的逐幀偵測閘門共用同一個偵測器實例 （同一模型、同一組合格條件：conf 0.25、bbox 高度門檻）。模型只載一次。
  • 演算法（stride / merge / buffer / max_gap）從 prescan_filter_valid_video.py 逐段移植； P1 用 PrescanParityTests 對「同一支影片、桌面腳本用相同 scale 的 .pt 跑出的區段」比對，容忍區段邊界 ± buffer 內的差異。
  • benchmark 的「有效處理 FPS」「每幀成本」都只統計有效區段內的幀，不被大段空景稀釋。
待對齊

prescan 的 stride / min_height / buffer_sec / max_gap_sec 要跟正式後端目前的設定一致 （見 §12 待你確認）。桌面 parity 參考的 --engine 要換成與 detectorModel 同 scale 的 .pt（如測 yolo26s 就用 yolo26s.pt），否則區段基準會因模型不同而對不齊。

Core ML 運算單元

Core ML 只能指定四種組合，不能單獨 pin GPU。四種都要掃：

MLComputeUnits意義本測試角色
.cpuAndNeuralEngineANE + CPU（GPU 排除）預期的正式值；相機/繪圖情境下 GPU 通常在忙
.cpuOnly純 CPU下限基準 / 相容性 fallback
.cpuAndGPUGPU + CPU（ANE 排除）對照 GPU 路徑
.all系統自選 CPU/GPU/ANE對照「交給系統」是否更好或更抖
已知文件錯誤

主 repo 的 docs/developer/hrnet_coreml_conversion.md 範例寫 .all。依 yolo-ios-app 實測與 ANE 論文，即時 / 連續推論情境應為 .cpuAndNeuralEngine。本測試會用數據確認，並回頭修正那份文件。

量測基準：真機才算數

  • Host（Mac coremltools）的相對排序在 yolo-ios-app 實測中翻盤過兩次。Host 數字只當假設。
  • ground truth = 真機的 Xcode Core ML Performance Report（隔離延遲、per-layer 運算單元配置）+ instrumented App build（含 pipeline contention、thermal）。
  • .mlpackage 目前只在 Linux 轉過、沒跑過 CoreML runtime。P0 第一件事是在 macOS 確認能載入、能推論、heatmap 對得上 PyTorch。

HRNet-W48 是重模型

63.7M 參數，遠重於 yolo-ios-app 那顆 YOLO26n-pose（~3M，A19 上 ANE 3.9ms/幀）。預期單幀 HRNet 推論落在 約 8–30 ms/幀（ANE，依晶片世代）這個量級 —— 但這是要靠這次測試確認的數字，不是承諾值。

03 模組架構

RunnerPoseKit 是一個 Swift Package：對外一個乾淨的 async 串流 API，對內一條零拷貝、 有界並行的推論管線。BenchApp 與日後的 Flutter plugin 都只透過這個 API 使用它。

對外 API

// 一幀結果 —— 座標皆為原圖像素，schema 對齊現有 pipeline
public struct RunnerPose {
    public let frameIndex: Int
    public let timestamp: CMTime
    public let bbox: CGRect
    public let joints: [Joint]        // 23 點 · (x, y, score)
    public let valid: Bool            // 是否通過有效性閘門
}

public enum DetectorModel { case yolo26n, yolo26s, yolo26m, yolo26l, yolo26x, visionHuman }

public struct Config {
    var computeUnits: MLComputeUnits = .cpuAndNeuralEngine
    var detectorModel: DetectorModel = .yolo26n   // S0 prescan 與 S2 共用；跑完 §08 再定
    var prescanStride: Int = 8        // prescan 取樣間隔（對齊桌面腳本）
    var prescanBufferSec: Double = 1.0
    var prescanMaxGapSec: Double = 1.0
    var detectorCadence: Int = 6      // 每 N 幀跑一次 YOLO，其餘外推 bbox
    var maxInFlight: Int = 3          // 管線深度 / 記憶體上限旋鈕
    var adaptiveThermal: Bool = true
}

public actor RunnerPoseEngine {
    public init(config: Config) async throws
    public func warmUp() async                              // dummy 推論，載權重
    public func poses(for video: URL)
        -> AsyncThrowingStream<RunnerPose, Error>           // 串流消費
    public func lastRun() -> BenchReport                    // 逐階段 ms / 記憶體 / 熱
}

actor 保證單一模型實例、序列化 ANE 存取。AsyncThrowingStream 讓 BenchApp（顯示進度）與 Flutter plugin（轉成 Dart Stream）用同一介面。 BenchReport 是量測資料的唯一出口。

內部管線（prescan 預掃 + 有界並行）

S0 prescan 先跑一遍 —— 用 Config.detectorModel 選定的偵測器每 prescanStride 幀取樣，產出有效區段清單。之後 S1–S5 五個 stage 各自一條 Task，用深度受限的 channel 串接（上限 = maxInFlight），且 只處理區段內的幀；讓 ANE 不必等解碼、也不會因前段跑太快把記憶體塞爆（back-pressure）。 每個 stage 進出各一個計時點。

Stage元件關鍵作法
S0PrescanFilter選定偵測器每 prescanStride 幀取樣（只 grab、不完整解碼）；命中幀併區段 + prescanBufferSec 緩衝 + prescanMaxGapSec 併接；演算法移植自 prescan_filter_valid_video.py；輸出 [CMTimeRange]，不寫檔

S2PersonDetector + BBoxTracker與 S0 共用同一個偵測器實例（Config.detectorModel）；每 detectorCadence 幀跑一次、在降採樣幀上；中間幀用上次 bbox + 速度外推；同一組合格條件當有效性閘門
S3CropWarp移植 box_to_center_scale + affine；vImageAffineWarp（Accelerate，預配置 temp buffer）；輸出 buffer 取自 CVPixelBufferPool，直接是 model image input
S4HRNetRunner單一 MLModel；.mlmodelc 預編譯 + 快取編譯路徑；MLPredictionOptions.outputBackings 重用 heatmap 輸出；iOS 17 用 async prediction(from:)

另有兩個獨立取樣器：記憶體（每 250 ms 讀 task_vm_info.phys_footprint）與 熱狀態（監聽 thermalStateDidChangeNotification；adaptiveThermal 開時 據此調 detectorCadence 與處理幀率）。每幀迴圈包 autoreleasepool。

BenchApp（量測薄殼）

  • 單一 SwiftUI 畫面，Run 前可自由選：影片（檔名 / 解析度 / 幀數 / 長度）、偵測模型 yolo26n / s / m / l（picker，全部 bundle 在內）、運算單元四選一、detectorCadence 與 maxInFlight 旋鈕、warmup 幀數。
  • Run → 進度 + 即時 FPS；結果卡：總時間、平均 FPS、各階段 mean / p50 / p90 / max（含 S0 prescan 與 S2 偵測分開）、模型載入時間、峰值記憶體、熱狀態軌跡。
  • 每次 Run 的 BenchReport 記下這次的 (偵測模型, cadence, 運算單元, 影片, 裝置, 熱/電狀態) 組合 + 全部指標，append 到裝置上的結果清單；可在 App 內看歷次結果表、比較、整批匯出。
  • 「匯出報告」→ 分享 BenchReport JSON + per-frame CSV；「疊圖預覽」（可選）把骨架畫回影片檢查錯位。
  • 所以「偵測器選型」就是在 iPhone 上逐一選 n / s / m / l 各跑一輪、看累積的結果表決定 —— 不需要桌面腳本驅動。
  • BenchApp 不含任何推論邏輯 —— 全部在 RunnerPoseKit，確保量到的就是正式模組。

04 效能最佳化策略

目標不是「能跑」，是把每一個會讓 ANE 閒置、讓記憶體長大、讓延遲抖動的點都消掉，做到可直接上線。 每一項都要量測前後差異並寫進報告；沒有實測收益的最佳化不留。

模型層

手法為什麼驗證
固定 .cpuAndNeuralEngineGPU 在相機 / 繪圖情境常被佔用；ANE 專用且能效佳四單元 sweep 比 latency + jitter
.mlmodelc 預編譯，快取編譯結果路徑首次 compile 數百 ms～秒級，不該每次啟動重付冷 / 暖載入時間對比
outputBackings 重用 heatmap 輸出 buffer[1,23,96,72] fp16 ≈ 317 KB／幀，免每幀 malloc / freeInstruments Allocations 前後
啟動時 warmUp() 跑一次 dummy 推論首幀含 ANE 權重載入 / JIT，不該混進統計首幀 vs 穩態延遲
輸入用 IOSurface-backed CVPixelBuffer image input免一次 CPU 端 copy，讓 CoreML 直接 DMA 給 ANEwarp→predict 交界計時

影格路徑（零拷貝）

手法為什麼驗證
alwaysCopiesSampleData = false免每幀複製整張 framedecode ms 前後
CVPixelBufferPool 供 288×384 crop重用而非每幀新配置，記憶體曲線平穩Allocations · 長影片 footprint
warp 全程在 IOSurface buffer 上，不進 [Float] / UIImage每次 bridge 都是一次拷貝 + 一次格式轉換Time Profiler S3 佔比

管線並行

手法為什麼驗證
五 stage 各一 Task，bounded channel 串接單執行緒序列會讓 ANE 在解碼 / warp 時整段閒置；深度 3 的管線把有效 FPS 拉近 1 / max(stage)序列 baseline vs 管線版有效 FPS（預期最大單一收益）
channel 滿則擋解碼（back-pressure）前段跑太快會把 in-flight buffer 堆到 OOM長影片記憶體上限是否穩定
maxInFlight 可調（舊機設 2）記憶體上限 ≈ inFlight × 單幀 buffer 組舊機記憶體 vs 吞吐取捨

偵測器（S0 + S2，與 HRNet 同量級，是主要可省點）

手法為什麼驗證
S0 prescan 先切掉空景，S1–S5 只處理有效區段跑者入鏡前後的空片段完全不解碼 / 不 warp / 不進 HRNetkept_ratio；端到端時間 vs 全片處理
S0 與 S2 共用同一個偵測器實例模型只載一次、只編一次 .mlmodelc；prescan 只 grab 取樣幀不完整解碼模型載入次數；prescan 階段耗時
偵測模型 sweep：yolo26{n,s,m,l}（+ Vision）「單一大側面跑者」偵測很簡單，n 多半夠；但要用數據決定，弱模型跑勤可能贏強模型跑少各 scale × cadence：detect ms、bbox IoU、最終 keypoint 誤差 delta、模型大小
每 6 幀跑一次偵測 + 中間幀速度外推 bbox跑者 bbox 平滑移動，偵測頻率可砍 ~6×，detect 平均成本降約 5/6cadence sweep（1 / 3 / 6 / 自動），與上一列合併掃
偵測在降採樣幀（640 長邊）YOLO26 本就 640 輸入detect ms 前後
thermal 壓力下自動拉長 cadencethrottle 時優先保 HRNet長影片熱曲線

後處理與記憶體

手法為什麼驗證
DarkPose 用 vDSP（argmax / 分離式 Gaussian / Taylor）純 Swift 迴圈對 23×96×72 ≈ 159K 點／幀會吃滿一顆 CPUnaive 迴圈 vs vDSP，postproc ms
直接讀 MLMultiArray.dataPointer轉 [Float] = 一次 636 KB 拷貝／幀Allocations
單一 engine / 單一 model 實例（actor 保證）HRNet 權重 fp16 ≈ 120 MB，不可重複載peak footprint
每幀迴圈包 autoreleasepoolCMSampleBuffer / CVPixelBuffer 及時釋放長影片 footprint 是否平坦
（可選）heatmap decode 移 Metal kernel若 profile 顯示 postproc 仍是瓶頸只在量測支持時才做
最佳化順序

先做不影響精度的低風險項（管線並行、outputBackings、buffer pool、vDSP DarkPose、 零拷貝影格路徑），量一版 optimized。再視 profile 決定要不要動會影響精度的項 （偵測器 cadence 外推，必須跑 §07 的比對）與高複雜度項（Metal DarkPose）。 每項單獨一個 commit、單獨一行 benchmark delta，不要一次全上。

05 執行階段 P0–P5

相依鏈：可行性 → 正確的 naive 版（正確性 + 效能基準線）→ 逐項最佳化 → 量測矩陣 → 報告 → 整合。 合計約 3.5–5 週（單人）。

P0前置與可行性驗證~2–3 天
  • 建獨立 git repo runner-pose-ondevice（結構見 §10，不是 runner-analysis-pipeline 的子目錄）：
    • Mac（主要開發，Xcode / SwiftPM）：例如 ~/Developer/runner-pose-ondevice —— 整個 repo。
    • Linux catslab：/home/jeter/runner-pose-ondevice（同 repo 的 clone），只跑 scripts/ 與 testdata/，RunnerPoseKit/ 不在這台編。

07 精度比對方法

「會不會降精度」是核心問題，方法要嚴謹，否則 crop 沒對齊或偵測器 cadence 外推的誤差 會被誤讀成模型精度損失。

對齊策略（關鍵）

誤差必須在完全相同的 288×384 crop 上比。做法：模組逐幀匯出它實際用的 bbox (x1,y1,x2,y2) 與 affine 矩陣；桌面端用同一個 bbox 重跑 HRNet 產 ground truth。不要各自跑各自的偵測器 —— 那樣量到的是偵測器差異，不是姿態模型差異。

偵測器選型 + cadence 的精度影響（§08 先導）

detectorModel（yolo26{n,s,m,l}）× detectorCadence（1 / 3 / 6 / 自動） 會讓部分幀的 crop 偏移。以 yolo26x / yolo11x 桌面逐幀偵測為 bbox 基準， 比每組的 bbox IoU 與 最終 keypoint 誤差：額外誤差要小於 §09 的精度 warn 帶，否則升 scale、調低 cadence 或加 Kalman 濾波。選型結果（含被淘汰的 scale 數據）進報告。

三方對照

版本環境用途
Python HRNet FP32桌面 PyTorch（現有 pipeline）最終 ground truth
CoreML FP32額外轉一份（--precision float32，已有指令）隔離「轉換 + 移植」損失，與 FP16 無關
CoreML FP16（正式）模組，各運算單元實際要部署的版本

差異拆解：CoreML-FP32 − Python-FP32 = 轉換 + Swift DarkPose 移植的誤差； CoreML-FP16 − CoreML-FP32 = 純 FP16 量化損失； 若 .cpuAndNeuralEngine 與 .cpuOnly 結果不同 = ANE 的 fp16 計算路徑差異。

桌面對照腳本

# scripts/make_ground_truth.py
# 讀模組匯出的 per-frame bbox，對同一批影格用桌面 HRNet 產 keypoints
python scripts/make_ground_truth.py \
  --videos testdata/videos \
  --device-bboxes runs/<device>/<video>_bboxes.json \
  --out runs/ground_truth/<video>_kpts.npz

# scripts/compare_accuracy.py
# 裝置輸出 vs ground truth → per-joint 誤差表 + PCK + 圖
python scripts/compare_accuracy.py \
  --device runs/<device>/<cu>/<video>_kpts.json \
  --truth  runs/ground_truth/<video>_kpts.npz \
  --bbox-diag auto \
  --out report/accuracy/<device>_<cu>_<video>/
預期

依轉換報告，FP32 轉換近乎無損（1e-6 量級）。FP16 通常在 heatmap 尺度造成 sub-pixel 位移，回原圖後多半 < 1–2 px。 真正的風險點是 DarkPose 移植（高斯 kernel、邊界處理、Taylor 展開的數值細節）與 腳部 6 點（本來信心就低）。這兩處要重點看。

11 整合進主流程

目標：把 2D 姿態這一段從 server 移到裝置，上傳量從「整支影片」降到「幾百 KB 的 keypoints JSON」， 其餘階段暫時不動。

現況 → 目標

現況目標
上傳Flutter → uploadVideo → serverFlutter 在裝置跑 runner_pose → 上傳 keypoints JSON
tracking + HRNetserver run_analysis() 前兩階段裝置 RunnerPoseEngine（本模組）
左右腿 / 3D / 步態 / overlayserver不變（server，吃上傳的 keypoints）
影片上傳、留 server留裝置（使用者可選擇性上傳供標註）

步驟

  • runner_pose federated Flutter plugin，iOS 端 Pigeon typed channel 包 RunnerPoseEngine；AsyncThrowingStream → Dart Stream（帶進度）。
  • 主 App 錄影 / 選片後，先在裝置跑 plugin 得 keypoints，再上傳 keypoints 取代上傳影片。
  • feature flag：新舊路徑並存，可 A/B 對比結果與體感。

後端改動（最小 · 列為整合待辦，不在本 repo）

  • routes/upload.py 加 POST /analyze/keypoints：收 keypoints JSON + metadata。
  • core/pipeline.py 加一個 PoseSource.PRECOMPUTED_2D 分支，跳過 tracking + HRNet，直接從上傳的 keypoints 進「左右腿修正」。
  • keypoints schema 就是本模組 P1 鎖定、且與現有 HRNet 階段輸出一致的那份 —— 後端不需要新格式。
